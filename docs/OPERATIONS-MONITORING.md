# Production monitoring and follow-up

GitHub's recovery coordinator runs on relevant workflow completion and its scheduled fifteen-minute checks. It retries only allowlisted failed jobs with recorded temporary failures, retained stages, eligible retry times and remaining attempt budget. It does not blindly retry invalid content or publishing. GitHub schedule delays are possible; this is not an exact alarm clock.

A continuing Codex heartbeat named Content Empire health and recovery is active every fifteen minutes in the existing chat. It checks both system repositories, investigates failures, reuses valid work, applies authorized routine fixes, verifies outputs and updates documentation. It is ongoing health monitoring across the four systems, not repeated reminders about one video. The first scheduled heartbeat executed on November 18 at 2:53 AM Chicago and inspected both repositories, approval settings, the publishing snapshot and recovery records. This verifies scheduled follow-up in the current environment, not execution while the computer/app is unavailable. The desktop/app follow-up must not be described as guaranteed cloud execution when the computer is unavailable; local-file work requires the machine and app to be available. Video generation stays on cloud runners.

No automatic owner approval is enabled. Unrecoverable failures stay visible in Studio and work-items records. A rendered video is not complete until its encoded media/audio, narration and actual Studio delivery have been checked. Independent transcription is not human listening.
